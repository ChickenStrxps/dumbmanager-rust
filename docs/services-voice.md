# Voice integrations and scoped MCP

`src-tauri/src/services/voice.rs` implements the original AI integration, voice session, approval, and scoped tool request shapes for the native dispatcher. It stores its own configuration, session leases and approval receipts in the Rust app's service data directory; voice credentials use current-user Windows DPAPI through the shared runtime. Nothing is inherited from another installation. Provider calls use fixed HTTPS endpoints, a 12-second timeout, no redirects, bounded responses and sanitized error messages. Testing and provisioning occur only after an explicit user action.

OpenAI uses `gpt-realtime-2.1` by default but permits a configured model. It requests a 60-second client secret and the existing UI connects directly to `/v1/realtime/calls`. A successful provisioning test does not prove model conversation, microphone or audio playback. The client secret's lifetime limits creation of new sessions; it does not itself forcibly stop an established session, and OpenAI permits reuse during its lifetime. Backend tool grants are independently checked against the session lease. The browser is responsible for closing its direct connection at its configured deadline. See [OpenAI client secrets](https://developers.openai.com/api/reference/resources/realtime/subresources/client_secrets/methods/create).

Gemini uses the configured model and voice, requests a single-use token with RFC3339 expiry, and puts the complete Live setup in `bidiGenerateContentSetup` without a field mask. Google's raw [Live API reference](https://ai.google.dev/api/live#authtoken) states that this causes the provider to take the complete setup from the token request, ignoring the WebSocket setup. The browser uses the constrained WebSocket endpoint. Google documents that sessions may need resumption after about ten minutes; the existing UI stops on `goAway` and does not resume automatically. A provisioning receipt is not an audio or external-client test. See [Google ephemeral tokens](https://ai.google.dev/gemini-api/docs/live-api/ephemeral-tokens).

Enabled integrations have separate versioned allowlists. The current intentionally narrow native set covers local status, itch list/get/history/brief, saved context, project listing, and reviewed capture/repeat. It does **not** expose arbitrary shell commands, integration administration, user acceptance, sending, publishing, or the full original capability inventory. The four tools are `dumb_search`, `dumb_describe`, `dumb_call`, and `dumb_job`; there is no job executor in this scoped set. Reads call the native dispatcher and can transmit granted data to the selected provider. Actions first persist an exact argument receipt and require an owner decision; version changes, session closure, or expiry revoke pending requests. A decision durably marks dispatching before calling the native handler. Concurrent/repeated decisions cannot dispatch it again; interrupted or unconfirmed dispatches surface as uncertain, including after restart. Receipts are bounded by the shared runtime document capacity and remain durable rather than being silently purged.

`mcp_response` and `serve_stdio` implement bounded newline-delimited MCP JSON-RPC. No listener starts automatically. On Windows, a named per-logon-session mutex serializes the voice document and secrets between processes; network requests never hold it. The stdio entry point is `dumbmanager-mcp.exe --profile mcp` (or `dots`).
Settings advertise the executable only when it exists beside the desktop app.
Its local connection check performs MCP initialization and explicitly reports
that an external client was not tested. Scoped HTTP MCP tokens remain unavailable;
the phone listener is not an MCP endpoint. Dots requires its own workspace access, a custom MCP plugin, and a configured secure tunnel or another supported MCP route; no undocumented Dots API or successful connection is assumed.

Verification: an isolated temporary Rust harness compiled these owned files against the actual core/runtime and passed 11 tests, with one helper test intentionally ignored in the parent process and invoked by the cross-process test. Coverage includes both local HTTP provider wire contracts, redacted provider errors, DPAPI ciphertext, session caps and expiry, changed permissions, exact-request conflicts, concurrent and cross-process single dispatch, uncertain recovery, and stdio protocol framing. No real credentials, provider account, microphone, browser audio, Dots, tunnel or external MCP client were used. Full app integration and its checks remain the parent's responsibility.
